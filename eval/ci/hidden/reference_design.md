# Reference design (hidden from the agent): agent-native CI

The real system was built by one engineer with a coding agent in about two months (~12.5k lines
of Go, 177 tests). It works and builds itself. Its own backlog is the best record of what it lacks.

## What the real system did

- **Scope.** Built new, Go. Later the backlog declared "Jenkins feature parity" an explicit
  non-goal and narrowed the product to "usable in production for a small team, or as an
  agent-operated CI substrate". Out of scope: plugin ecosystem, Groovy-style templating,
  multi-platform agents, rich UI, notification zoo.
- **Decomposition.** `master` (webhooks, DAG building, scheduling, log store, gRPC + HTTP APIs),
  `worker` (runs each task in a Docker container, streams logs, reports results), `cli`, and an
  `mcp` server exposing all operations as tools to agents. Contracts in protobuf/gRPC; one
  style throughout. Domain packages: dag, pipeline parser, scheduler, worker registry,
  logstore, scm, container, secrets.
- **Execution.** Pipeline as YAML in the repo. A build is a DAG of tasks with `depends_on`;
  cycle detection; Pending → Ready → Scheduled → Running → Passed/Failed/TimedOut/Cancelled;
  failure cascades Skipped to dependents. Scheduler loop every 500 ms, bin-packs ready tasks
  onto workers by CPU/memory/disk. All tasks of a build share a named Docker volume as
  `/workspace` (no artifact copying). Heavy caches (gomod, npm, pip, vuln DB) are persistent
  named volumes reused across builds. Entrypoint normalised to `sh`.
- **Agent interface.** MCP tools: submit_build, get_build, list_builds, watch_build,
  get_task_logs (paginated), diagnose_build (failed tasks, error lines, skipped dependents),
  suggest_fix, get_failed_builds, retry_build (failed tasks only, or full), cancel_build.
- **Integrations.** Linters, scanners, SonarQube and AI code review are generated by the
  pipeline parser into the DAG as tasks (depend on clone, images and caches injected). Adding
  one is parser/registry code, not scheduler code. SCM reporting for GitHub and GitLab behind
  one interface; container runtime behind an interface (Docker, mock).
- **Security.** HMAC-verified webhooks; scoped in-memory secret store with log scrubbing;
  mTLS master↔worker; token auth on gRPC.
- **Ops.** Prometheus metrics; slog structured logging; file-backed durable log storage;
  worker heartbeats; draining; workspace volume cleanup.

## Known weaknesses (basis for level 4)

From the real backlog, P0/P1:
1. Build state is in memory: a master restart wipes all build history (P0 "durable build
   state", Postgres/SQLite as source of truth, memory as hot cache).
2. One shared API token: no per-user or per-agent identity; no audit log; REST API
   unauthenticated. No first-class agent identity, so no budgets or rate limits per agent.
3. Worker death needs a manual `retry_build`; no automatic reassignment.
4. Builds, logs and cache volumes grow without bound; no retention.
5. Docker isolation only, while agents submit untrusted code (needs gVisor/Firecracker-class
   sandboxing before external agents get submit rights).
6. Worker labels parsed but ignored in scheduling; no pipeline-level timeout.
7. Agent loop gaps: logs are free text (agents regex them) instead of structured events;
   no per-task re-run that reuses unchanged upstream outputs; no build-diff tool; no
   pipeline validation tool; no flake history; no cost/budget stop signal for agent loops.
8. No graceful upgrade or backup/restore.

## Calibration

- A design that proposes building a full Jenkins replacement with plugins, UI and
  multi-platform agents, for 2 engineers in 3 months, is weak on scope regardless of quality.
- Keeping Jenkins for humans and adding an agent-facing API/MCP layer, or adopting an existing
  open-source CI and adding the agent layer, are legitimate alternatives to building new; each
  must be argued from the facts (plugin debt, one part-time maintainer, agent needs).
- Kubernetes, a service mesh or a message bus for 5 VMs need strong justification.
